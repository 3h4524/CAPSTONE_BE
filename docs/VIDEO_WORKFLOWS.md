# Video from Mockup — Standard MVP

## Scope

The executable pipeline is Product Input → Apply Mockup → Mockup Approval → Generate Video → Review Video → Export ZIP. A run snapshots one owned product and workflow revision. Standard rendering remains available. AI Scene Video is also implemented: each video node can contain one to four AI scenes, each with its own source image, prompt template, duration and camera/motion/lighting settings. Scene durations are 4, 6 or 8 seconds, up to 30 seconds total. Mixing Standard and AI scenes is intentionally deferred until this AI-only scene flow is validated.

Standard template catalog version 2 contains Product Showcase, Design Detail and Variant Showcase. AI scene templates are Cinematic Product Showcase, Macro Detail Reveal, Lifestyle In-Use, Creator POV / UGC, Everyday Story Moment and Signature Product Reveal. Their versioned base/common prompts, allowed settings and defaults live in `video_templates.effects_config.aiVideo`; if the seed has not been applied, the API falls back to the same built-in catalog. Each run snapshots the exact template version, user settings and compiled prompt, so later catalog edits do not rewrite an existing video.

A cancelled run with a completed Generate Video step can be reopened by regenerating one already stored AI scene. All other AI scene clips must also be stored and their provider/model options must remain compatible. The scene-specific quote and paid confirmation cover the selected clip; the render reuses the other stored clips, creates a new video version and returns it to review. A cancelled run without a completed video or stored target clip cannot be reopened this way. Any stopped run can instead be resumed (`resume` run action, `POST /api/run-groups/{id}/resume` for a whole group, `WorkflowRunStops`): its cancelled steps are opened again and it carries on from where it stopped, keeping the finished steps and the stored AI clips. Settings sent with `resume` (a scene made longer...) replace the video's, and only the clips they change are made again; a video the stop left unfinished is marked `failed`, so it is not counted against the plan and is made again under the same version when nothing changed. Completed runs remain closed.

Focused regression command: `dotnet test tests/APCS.Application.UnitTests/APCS.Application.UnitTests.csproj -- --filter "FullyQualifiedName~WorkflowRunServiceTests|FullyQualifiedName~AiShotQuoteServiceTests"`.

### MiniMax H3 / H3-Lite prompt format

Brand Focus now pairs the slow push-in with one natural upward-looking action: the model gently raises their gaze, follows with a small chin lift, then settles looking slightly above the lens with natural breathing. Keep the existing head/face in frame when visible alongside the design; shorten the push rather than cropping into the logo alone. Preserve the source pose, hand placement and setting, with a smaller adjustment if the opening gaze is already raised. Do not infer a face absent from the crop. Explicit P1 actions replace this default performance. The default action is retained in the brand guardrail after Gemini editing; a conservative text check falls back to the compiler draft when the rewrite omits the gaze or chin action. See the [Brand Focus audit](BRAND_FOCUS_PROMPT_AUDIT.md).

Built-in Fabric Detail Close-Up uses a small, slow arc toward frame-right (`orbit_right`), maintaining approximately the same camera height, distance, focal length and detail scale. The opening detail stays in frame and in focus; shorten the arc for a tight crop and stop before passing behind the shoulder or revealing the back. Restrained background parallax and natural foreshortening establish the movement. Brand Focus retains its small, slow push-in and existing-design/unbranded fallback. Both preserve their distinct body motion, source lighting and setting; explicit P1 actions replace default body actions. Mandatory `fabric_detail_guardrails` and `brand_focus_guardrails` survive Gemini editing. Matching editor briefs and conservative phrase checks retain each camera direction; invalid rewrites keep the compiler draft. These checks do not prove visual fidelity. Catalog version stays 12: recognized persisted Fabric Detail built-in push-in prompts/defaults upgrade to the arc, while custom creative text and other camera defaults retain their direction. Changed text/settings change new preview fingerprints/cache keys; confirmed snapshots keep their stored prompt. See the [Fabric Detail audit](FABRIC_DETAIL_PROMPT_AUDIT.md) and [Brand Focus audit](BRAND_FOCUS_PROMPT_AUDIT.md).

New Economy `minimax_h3_lite` and Premium `minimax_h3` scenes use the same application I2VA content format: a first-frame alignment instruction, one `integrated_multimodal_description` beginning with `[Shot 1]`, `overall_soundscape`, and `non_diegetic_music`. Formatting happens before optional RAG trimming and fingerprinting, so review, quote, and generation share the exact final prompt. The source image remains a separate `first_frame` API content item. Confirmed historical snapshots retain their stored prompt. The H3 guide is the source of this format; applying it to Lite is an application choice, not a separately verified official Lite prompting specification or evidence of equal video quality.

For the built-in Natural Motion prompt without P1, both H3 and H3-Lite preserve the source viewing direction and lighting; the effective scene settings record `source_view` and `source_image`. P1 retains its existing template controls and explicit start/action/end plan. Custom catalog base prompts are preserved as draft inputs. See [the H3 prompt audit](MINIMAX_H3_PROMPT_AUDIT.md) for actual before/after prompts, verification, and limits of the evidence.

Built-in Profile Tracking (formerly displayed as Right Camera Arc) uses a slow, stabilized H3/H3-Lite arc toward frame-right. Total angular travel is approximately 30–40 degrees across the whole shot, capped at 40 degrees and shortened when the opening view is already near profile. The camera eases gently into and out of the glide and stops at the side-profile boundary without travelling behind the shoulder or revealing the back. The model keeps the opening pose and gaze; natural perspective and foreshortening are allowed. Non-P1 effective controls remain `orbit_right`, `source_view`, `source_image`. A mandatory `profile_orbit_guardrails` part preserves the camera boundary and product rules after Gemini editing. The editor receives matching instructions. Conservative text validation requires `with small amplitude at slow speed` and `30-40 degrees`, and rejects the previous rear-three-quarter/large-amplitude/fast-speed directions or degrees-per-second wording; failure keeps the new slow compiler draft. These checks can reject equivalent wording and do not prove geometry or visual fidelity. The angle range is application policy, not a documented MiniMax camera parameter or validated guarantee. Rigid products keep their shape instead of receiving fabric motion. Explicit P1 actions and custom catalog prompts retain their own direction/defaults. The code-owned catalog entry restores the Profile Tracking display name even from a persisted Right Camera Arc label. See [the Profile Tracking audit](PROFILE_TRACKING_PROMPT_AUDIT.md) for the exact prompt and tests. Preparation still uses the existing two Gemini stages.

After deterministic planning succeeds, `VideoPromptPreparationService` optionally analyzes the actual prepared H3/H3-Lite first frame with Gemini, then edits the draft into continuous shot prose. Preview and workflow planning both use this step before quote/snapshot creation. `MiniMaxFirstFramePreparer` supplies the same crop/resize policy to analysis and provider submission. Standard, legacy providers and confirmed historical prompt snapshots bypass preparation. Custom creative directions are supplied to the editor as data; their original text remains in the trace, while the provider receives the rewritten description and retained preservation rules. Preparation never promotes Economy to Premium: model name/key and per-second price stay with the selected scene. MiniMax request ratios remain explicit for Lite and adaptive for H3.

Preparation uses the existing `Gemini:TextGeneration` credentials/model and two generation requests per uncached eligible scene. `VideoPromptPreparation:Enabled` defaults to `true`; set it to `false` to retain deterministic prompts. `VideoPromptPreparation:TimeoutSeconds` defaults to 45, bounded to 5–120 seconds per scene across both requests. No image/video generation is triggered by preparation. It does incur configured Gemini analysis/text charges in a running system. Frames over 12 MB fall back rather than changing the analyzed pixels to fit an inline request.

Economy optimization should be evaluated as total Gemini preparation cost plus video generation/retry cost per accepted clip. The current quote estimates video seconds only and does not include Gemini token charges. Structured prompting and image analysis do not establish that Lite matches H3 quality; generated video evidence is required for that claim.

Prepared traces are cached for 24 hours by owner, source identity/hash/revision/storage version, crop, aspect ratio, duration, model key, draft trace and preparation version; fallbacks are cached for two minutes. Cache misses, eviction or concurrent requests may produce a different rewrite. Existing quote/fingerprint checks still require review when the prompt changes; confirmed quote snapshots are reused without rewriting. The preparation version is `h3_grounded_v1`, independent of catalog `PromptVersion`. A cache outage does not block preparation.

`AiPromptTrace.Preparation` records `prepared` or `fallback`, analysis/editor models, prepared PNG SHA-256, opening observations and uncertainties. Original draft parts remain excluded from the provider prompt; included parts reconstruct the exact final prompt. Preservation/source/template guardrails are appended unchanged after the edited description. Invalid JSON, injected structural markers, excessive length, provider errors and preparation timeouts retain the entire deterministic prompt with a warning. Caller cancellation propagates. Observations and rewrites are model outputs, not verified OCR or semantic proof of instruction adherence. Audio retains the deterministic policy; the image analyzer does not infer sound from a still image.

### Optional T-shirt studio keyframe

Cinematic Product Showcase can start from either the approved mock-up or an optional Gemini Image studio keyframe. Direct mock-up mode is the default and makes no image-generation call. Studio mode currently supports T-shirts with a hanging/window-light or flat-lay layout. The user first requests a quote; an exact matching frame is returned for reuse at no new image cost, otherwise the UI confirms the configured per-image estimate before generation. New images remain pending until reviewed and approved.

Approved frames are stored as `mockup_images.source_type = 'ai_generated'`, role `VideoScene`. Their source id/hash/revision, layout, aspect ratio, prompt version and fingerprint are kept in the existing regions JSON under `studioFrame`. This lets previews, approvals and storage reuse the normal asset path without adding columns. The video planner verifies that metadata against the current approved source and rejects pending, rejected, stale, cross-product or mismatched frames. On eligible scenes it sends the same approved frame to the snapshotted video provider as the first image, while scene-specific camera instructions remain independent. The frame can be reused by another workflow for that product only while its source and settings still match.

The Showcase prompt uses restrained motion controls suitable for a single start image: locked, slow push-in/pull-back, or a subtle pan. It limits camera travel across the whole clip, keeps the set stable, and prohibits abrupt zooms, orbits and background changes. New scenes use MiniMax H3 at 768P; keyframes do not change the provider/model routing captured in the scene snapshot.

Source requirements are deliberate. Product Showcase and Signature Reveal can animate an approved product-only mockup. Macro Detail Reveal accepts either an approved artwork/detail image or a marked Artwork/Detail region; the backend crops that region from the source PNG and requires at least 512 pixels on its shortest side. A white-background shirt image is therefore usable if the printed area is marked and sufficiently large; otherwise add/approve a close-up. Person templates require an approved Lifestyle source with the adult already visible and explicit rights confirmation. The video model is not asked to invent a model/person from a blank product shot. The existing Lifestyle mockup flow can create that source from an adult reference photo.

AI prompts are composed as separate snapshot sections: versioned template base prompt, versioned P1 action/continuity rules, product and approved-source context, optional verified RAG experience, and immutable product/artwork guardrails. The RAG section is limited to three owner-scoped verified lessons and 1,500 characters; it cannot override source or product-preservation rules. User directions cannot replace the final guardrails. The provider factory resolves the immutable provider/model pair captured per AI scene. New scenes use the official MiniMax V2 image-to-video API with `MiniMax-H3`, 768P and the approved image as `first_frame`. H3 derives image-to-video ratio from that frame, so the backend crops it to 9:16 or 16:9 before submission. Historical Veo scenes keep their Gemini/Veo routing. The renderer fits the resulting clip into the selected final output format.

Upload mockups, mark protected product/artwork/detail regions directly on the image and approve the current metadata revision. The upload service assigns the product artwork group and Hero role by default. Role and variant remain under Advanced information, and the group selector is hidden when the product has only one group. Editing metadata increments the asset revision and removes its approval. Images are normalized to immutable PNG sources. The renderer produces silent 30 FPS H.264/yuv420p MP4 in Square 1080 × 1080, Portrait 1080 × 1920 or Landscape 1920 × 1080, up to 100 MB. Standard videos are 3–15 seconds (12 by default); AI scene videos are 4–30 seconds. Existing workflows without an output format default to Portrait. Review always addresses a video ID, review revision and run revision. Re-render preserves old versions; retry reuses the same logical candidate at its checkpoint.

Standard motion presets include `contain_gentle`, zoom in/out, horizontal and vertical pans, and four diagonal pan directions. `contain_gentle` applies a small scale animation while retaining the complete image and is the version 2 default when no protected region exists. Crop motion is accepted only when its complete path contains the protected product or artwork region; otherwise the planner returns contain/static framing and a warning.

New workflows default to Auto template version 2, 12 seconds, fade, Varied motion, no caption and automatic image selection. The browser debounces storyboard requests and displays the exact backend `ScenePlan` through the same composition geometry package used by the worker. A stale preview response cannot overwrite newer settings. Scene order and motion move together; Reset to template clears selected IDs, order and motion overrides. Existing workflows retain version 1 when `templateVersion` is absent.

`GET /api/workflows/video-templates` returns Standard templates. `GET /api/workflows/ai-video-templates` returns the AI scene prompt catalog and allowed settings. A rerender request should include `expectedStoryboardFingerprint` from a current preview. The API replans from current approved asset revisions and returns conflict instead of enqueuing when the fingerprint differs.

## Combined with design generation

The same workflow can generate the designs and mock-ups that the video is made from. Prompt Synthesis, Design Image and Design Approval (`design-approval`) may sit between Product Input and Apply Mockup, each at most once, so the full line is Product Input → Prompt Synthesis → Design Image → Design Approval → Apply Mockup → Mockup Approval → Generate Video → Review Video → Export ZIP. `WorkflowCapabilityRegistry.RunOrder` holds that order and `WorkflowGraphValidator` requires one edge between each pair of neighbouring steps that are present. The six video steps are still required exactly once.

These design steps have no executor in a run. The canvas runs them first as a batch job for the whole batch (`api/batch-jobs`), and a run leaves their checkpoints `pending`. Design Approval reviews designs before mock-ups are composited; Mockup Approval (`approval-gate`) still reviews mock-ups before rendering. Product Input therefore carries a batch for the designs and, optionally, one product: the preview product of the scene editor, or the product of an AI video (see below).

Apply Mockup composites mock-ups as Cloudinary transformation URLs. Such a row (`source_type = 'generated'`) has no stored file or content hash, so it is not listed by `GET /api/products/{id}/mockup-assets` and cannot be planned or rendered. `POST /api/products/{id}/mockup-assets/import-generated` stores a PNG snapshot of each one (Cloudinary fetches the composite URL itself) and records its key, version, hash and size on the same row, at most 24 per call, newest first. Imported mock-ups stay `pending` and are approved at Mockup Approval like uploads. Their artwork group is the design image ID and their variant is the garment color, so a product with several approved designs has several groups and a video uses one of them. The canvas calls the import when the video part starts and from the Mockup Approval panel; the batch video panel (`useSyncGeneratedMockups`) imports again each time it opens, so mock-ups regenerated after the run group started come in. A mock-up regenerated after its template changed becomes a new row. Once that row is imported, `MockupSources.Superseded` treats the older row of the same design, template and garment color as replaced: the asset list, the run group's designs, the target resolver and the automatic pick of the planner leave it out, and a scene that named it moves to the newer row by template and color. The older row is not deleted and keeps its import and approval, so a video already made from it keeps its source. A newer row still pending replaces an approved older one, so its design waits at Mockup Approval for that review instead of rendering the outdated image.

## One video per design (batch video runs)

With a scene list (`WorkflowGraphValidator.SupportsBatchVideos`), the video part makes one video for each (product, design) the seller confirms, at most `WorkflowRunGroupService.MaximumTargets` (10) per run. Standard and AI scenes both qualify; what does not is the Product on Model pack (it renders one product's shared mock-up and character) and the legacy single-shot AI settings (`AiShotOptions` without `AiScenes`, which name one product's image). AI clips are billed per second, so the whole group's cost is quoted and confirmed once (see **AI cost**).

- **Start.** Once the mock-ups exist, the canvas imports them for every product of the design job (or of the batch) and calls `POST /api/workflows/{id}/run-groups`. The group (`workflow_run_groups`) snapshots the workflow and waits in `waiting_for_targets`. It counts as one full run.
- **Choose designs.** `GET /api/run-groups/{id}` lists every design (mock-ups grouped by `ArtworkGroupKey`) of those products. A design with at least one mock-up approved at its current revision gets a video. The response also resolves each design's scenes, so Mockup Approval and Generate Video can show which image each scene will use.
- **Scenes per design.** Product Input's product is only the preview product: the seller sets the scenes up on its mock-ups. `SceneSourceResolver` rewrites them for each design. A scene whose image came from mock-up template T in color C uses the design's own mock-up from T in C; an image from no template (an upload, a lifestyle shot) maps by its role when that role is not `Hero`; a scene may name its image with `AiVideoSceneOptions.Source` instead. A Standard workflow saved without any scene list (the editor shows one blank scene for it) gives each design that one scene, as long as the video, on its main mock-up, without a warning; a scene whose start frame was never chosen is treated the same way. A workflow with a scene order or manual selection keeps the automatic plan. While a run group waits, the scene editor browses the images of the first design that has an approved mock-up (`usePreviewDesign`), since a batch has no product in Product input. What is still missing follows `GenerateVideoConfig.MissingSourcePolicy`: `hero` (default, the design's main mock-up, with a warning) or `skip` (leave the scene out). `PUT /api/run-groups/{id}/overrides` keeps a seller's own pick for a scene of one design (`target_overrides`).
- **Scenes with a person.** An AI scene whose template shows a person (`AiVideoPromptCompiler.RequiresPerson`: Product On Model, Creator POV / UGC, Everyday Story Moment) starts from the design's own model photo, the Lifestyle mock-up made at Mockup Approval from an uploaded or library model photo (`LifestyleMockupService`, `ModelPhotoMockupService`). The resolver uses that image whatever the scene names, and a design without an approved one is an error (`"Scene N shows a person, and this design has no approved model photo"`), not a fall back to the flat mock-up: the clip is paid for and a flat photo has nobody to film. When a group starts, the system makes that model photo itself for every design whose scenes need one and that has none, approved or waiting (`PersonModelPhotos`): Ideogram, with the seller's Ideogram key, dresses the shared library's model photo for the product type (one person before a group, then by name) in the design's Hero mock-up, exactly as an AI lifestyle image is made at Apply mock-up (`LifestyleMockupService.GenerateForVideoAsync`). One paid image per design, shared by all its scenes with a person; a design whose scenes are all Standard or show nobody gets none, or that has one already, gets none. A design whose photo cannot be made (no library model for its product type, no mock-up, Ideogram failing) is named with the reason in the group's notice, and Continue tries it again (approving it at once in auto mode). The Run estimate lists these images at Ideogram's price, leaving out designs that already have one. Each waits for review like any mock-up, so manual Mockup Approval asks the seller to approve it and auto mode approves it. The seller can still make one from another model, or reject the design's mock-ups to leave it out. A scene image the seller picked for that design themselves (`target_overrides`) is kept as picked.
- **AI cost.** The seller sees what a Run costs when pressing Run (`GET /api/workflows/{id}/run-estimate`, `RunCostEstimateService`: design images for products without one, each product's AI clips and the model photos still to make). That is the only confirmation: no paid step afterwards waits for a quote token. `VerifyAsync` and `VerifyBatchAsync` only check that the clips can be made (AI video on the plan, the provider key, the scenes resolve); a quote token that still matches carries the prompt the seller reviewed into the render, and any other token is ignored. `POST /api/run-groups/{id}/ai-quote` and the run quote still return the cost of the clips not made yet, which the canvas shows when the seller starts something again or changes it (retry, resume, re-render with other settings) and skips when nothing is left to pay for.
- **Settings per design.** A design may have Generate Video settings of its own (scene list, duration, format, transition), stored in its `target_overrides` entry as `TargetOverride.Config` through `PUT /api/run-groups/{id}/design-config` (a null config shares the workflow's settings again; settings that fit one product only are refused, and the config validator applies). The design's scene picks stay beside it. Confirm and the group's scene preview use a design's own settings when it has them, and confirm checks the plan features each one needs (landscape output) while the videos are counted once. The group response gives each design its `config`: its own settings while waiting, then the Generate Video input its run renders with. In the canvas, "Video settings for" at the top of Generate Video (`DesignScopeSelect`) shows one design's settings on the node itself (`designScope` in the workflow store keeps the shared ones aside; Save always writes the shared ones); after confirm, choosing a design opens its run, as the bar above the canvas does, and its changes apply on re-render.
- **Settings per product.** Before a run, Generate Video can give a product of the batch settings of its own: the node's shared config keeps them under `productConfigs` (product id to a whole Generate Video config, at most 50, each validated as the shared one and required to fit a batch run). A design renders with its own settings (`TargetOverride.Config`), else its product's (`GenerateVideoConfig.ForProduct`), else the shared ones; the cost estimate prices each product from its own. A child run's config never carries `productConfigs`.
- **Export.** Each video's run exports its own package (Export ZIP). `GET /api/run-groups/{id}/export` counts the ready ones; `GET .../export/download` returns the link of `.../export/file`, one ZIP that puts every ready package's product folder side by side under one manifest (`RunGroupExportService`; a second design of the same product gets `<folder>__2`). The Export ZIP node downloads that ZIP while a batch video run is open.
- **Auto approval.** Mockup Approval's `mode` is `manual` (default) or `auto` (`ApprovalGateConfig`, `MockupAutoApproval`). In auto mode a new group approves, as its owner, every design's stored mock-up still `pending` (not a rejected one, an AI keyframe or a composite replaced by a newer one) and confirms itself; when confirming fails (too many designs, plan allowance) it stays in `waiting_for_targets` with the mock-ups approved. A single-product run approves its design's waiting mock-ups at the gate and goes on, AI scenes included. A group starts its AI clips by itself as well: their cost was shown on Run, so auto mode confirms without quoting. The batch quote lists each design's part (`AiShotQuoteResponse.Items`).
- **Confirm.** `POST /api/run-groups/{id}/confirm` uses the workflow's saved Generate Video settings (so scenes saved while choosing count), checks the allowance for N videos and that the plan includes AI video when any design renders AI clips, and creates one child `WorkflowRun` per design (`run_group_id`, `artwork_group_key`). Its definition names the design's product and artwork group, its Generate Video input is already resolved, and its steps up to Mockup Approval are `succeeded`. The runs are `queued`; `RunGroupPlannerWorker` plans them a few at a time, acting as their owner (the listing needs the seller), and queues their renders.
- **After that** each child run is an ordinary run: retry, review, re-render and export work on it alone, and settings sent from the canvas are resolved for its design again (`IRunTargetConfigResolver.ResolveForRunAsync`). `POST /api/run-groups/{id}/cancel` cancels every unfinished child run; `POST /api/run-groups/{id}/resume` queues the stopped ones again for the planner (a group stopped at Mockup Approval waits there again), and resuming one child run brings its stopped group back to `running`. A run that failed or was stopped, and a video that failed, are not counted against the Free or trial allowance (`UsageAllowanceService`), so retrying or resuming counts them again instead of using a second allowance.
- **Live updates.** Pages join `JoinRunGroup` on `/hubs/workflow` and receive `RunGroupChanged`, `RunChanged` (after a commit) and `RunProgress` (a heartbeat that changed the stage or added at least 5 points). While connected, the canvas does not poll the group or its runs; it polls every 15 s only when the hub is down.
- **Fair share of workers.** A seller has at most `WorkflowStateRepository.MaximumLeasedPerUser` (2) renders or exports leased at once; in streams mode a claim over that limit answers `not_due` so the worker tries the event again.

The frontend resolves `@apcs/video-composition` from `../CAPSTONE_BE/shared/video-composition`, and `Start-VideoDev.ps1` looks for the frontend in `../CAPSTONE_FE` first and `../../Frontend/CAPSTONE_FE` second. With npm the package must be installed as a copy (`install-links=true` in the frontend's `.npmrc`): Turbopack does not resolve a link that points outside the project.

## Setup

For this Windows workspace, `./scripts/Start-VideoDev.ps1` starts the Release API at localhost:5191, frontend at localhost:3000 and local media worker using installed smoke-test binaries. It creates a shared ephemeral worker secret in child-process environments, not a file, and refuses occupied ports instead of stopping existing processes. Logs are in ignored `artifacts/video-dev`. Stop the returned processes before rerunning; the secret changes each launch. This convenience launcher does not replace production secret/container configuration.

Keep existing PostgreSQL, Cloudinary, Redis and authentication configuration. Add the platform-owned MiniMax credential to the API's ignored environment file or secret manager as `MiniMax__ApiKey`; it is used for every new H3 request and is never exposed to the frontend or worker. Add `MediaWorker__ApiKey` to the same environment: a random 32–256-character secret. Do not put either credential in workflow JSON or frontend environment variables. Configure the worker value as `MEDIA_WORKER_API_KEY`; copy `media-worker/.env.example` to its ignored `.env` and replace the placeholder. Set `AI_SCENE_CONCURRENCY` from 1 to 4 to cap concurrently submitted/polled scenes per worker. The default is 1 so paid video requests are submitted sequentially; raise it only after confirming that the system MiniMax account handles concurrent generations reliably. Never use the placeholder as a real credential.

Apply the additive database-first schema to the intended database after taking the normal backup. The script reads `ConnectionStrings__DefaultConnection` without printing it. It includes nullable product custom fields and mockup-template ownership already expected by the source but absent from the inspected database, plus the nullable `mockup_images.garment_color` and `mockup_images.background_color` fields selected by the current entity mapping. It does not delete existing business rows or require EF migrations.

```powershell
dotnet build API/API.csproj -c Release
./scripts/Apply-VideoSchema.ps1 -Configuration Release
./scripts/Scaffold-Database.ps1 -Configuration Release -NoBuild
dotnet build Capstone.sln -c Release
```

Restart the API to load the new endpoints and worker key. The worker Dockerfile uses the backend repository root as its build context so it can copy `shared/video-composition` before installing and building the worker. From `media-worker`, with Docker Engine running:

```powershell
docker compose up --build -d
```

The container has Node, Remotion, Chromium, FFmpeg and ffprobe. It runs as a non-root user, one product render job at a time, with a renewable 2-minute lease, a 30-minute worker deadline and up to 3 queue attempts. Within an AI render job, scenes are processed sequentially by default and can be processed concurrently up to `AI_SCENE_CONCURRENCY`; additional worker replicas can process other products. The durable PostgreSQL `MediaJob` queue remains the source of truth. `APCS_API_URL` must be reachable from the container. The default host port is 5191; change it if the API listens elsewhere. Use HTTPS outside the local/container network and restrict `/internal/media-jobs` at the ingress; it is separately authenticated with the worker key.

Local worker development is also possible with Node 22+, FFmpeg/ffprobe on PATH (or `FFMPEG_PATH`/`FFPROBE_PATH`), `npm ci`, `npm run browser`, and `npm start`. Set process environment variables explicitly; the Node worker does not automatically load `.env` (Docker Compose does).

The frontend uses its existing `NEXT_PUBLIC_API_BASE_URL`, cookie session and query providers. New AI video uses the backend's system-owned MiniMax key, so Sellers do not add MiniMax on the API Keys page. The UI shows the whole Run's estimate once, on Run; later it shows the snapshotted model and estimate only for clips a change adds (other settings, a regeneration), never again for a retry or resume with the run's own settings. Gemini remains separately available per Seller for listing content, historical Veo jobs and optional generated keyframes. Install with `pnpm install --frozen-lockfile`, then `pnpm dev`. The old simulated workflow server is removed. Existing browser-only demo workflows are not silently imported into the real database.

## Seller flow

1. Open Workflows, select a batch and one product in Product Input.
2. Upload/select up to 8 mockups in Apply Mockup. Draw Product, Artwork or Detail regions on the image; drag or use the keyboard/buttons to move and resize them. Role and variant are optional advanced fields. Replacing an image means uploading a new immutable asset and selecting it; changing metadata invalidates approval.
3. Save the definition and Run. Open Mockup Approval, approve/reject current image revisions, then Continue with approved mockups. Runs without valid sources remain waiting for input.
4. In Generate Video, select Standard Showcase or AI Scene Video. AI Scene Video starts with one scene; choose among six templates, select an approved source (or auto-select), choose 4/6/8 seconds, and optionally expand Advanced for framing, angle, motion, intensity, lighting and a custom instruction. Add up to four scenes; total duration is capped at 30 seconds. The estimate uses the snapshotted MiniMax H3 768P price of $0.08 per generated second and is confirmed again at run time. Choose Portrait or Landscape for AI video output. Product-only mockups are suitable for showcase/reveal; macro scenes need a marked detail region or a close-up; person scenes need an approved Lifestyle image. Rendering progress is polled from durable state; the URL retains the run ID for refresh.
5. Review the completed video without autoplay. Inspect QA/warnings and source scenes. Approve the exact candidate, reject, edit/re-render, or download the MP4. Previous versions are viewable but cannot approve a newer candidate. Review Video's `mode` is `manual` (default) or `auto` (`ReviewVideoConfig`, `VideoAutoApproval`): in auto mode the finished candidate is approved as the run's owner and the run goes straight on to Export ZIP, unless its saved QA shows an incomplete decode or an Etsy `fail` (Etsy warnings do not stop it); such a video waits for review as in manual mode. Each child run of a batch video run follows the same setting.
6. Export runs only after video approval. Download approved ZIP when export succeeds. ZIP contains video.mp4, thumbnail.png, approved source PNGs and a provenance manifest, not prompts, credentials, signed URLs or internal provider metadata.

## Scene quality review and private video experience

The first supported quality-review scope is a `Product with Model`/Lifestyle source combined with `Lifestyle In-Use`. `POST /api/video-quality/runs/{runId}/videos/{videoId}/scenes/{sceneOrder}/evaluate` runs local evidence adapters on a stored AI scene clip. `GET` on the scene endpoint reads the evidence and seller observations; `PUT .../reviews` records a timestamped observation and confirmed/overridden correction target. The evaluation records `queued`, `running`, `completed`, `uncertain`, `skipped`, or `failed`; it does not affect approval or storage of the video.

The correction rule is transparent: an issue already present in the source suggests `source_image`; a Lifestyle-specific action or composition suggests `prompt_template`; product preservation, artwork, anatomy, and shared continuity suggest `prompt_rule`; a seller-marked conflict after an applied lesson suggests `rag_experience`; otherwise it remains `unknown`. H3 is fixed for this stage, so neither the API nor reporting exposes a “model fault” category.

Confirmed non-source/non-unknown observations may create a candidate `VideoExperience` through the existing `IRagService` ingestion queue. Video experience is private: public `/api/rag` ingestion and search reject it. `VideoContextRetriever` filters owner, template, H3 model, action scope, and verified status before vector top-K. `PUT /api/video-quality/lessons/{lessonId}/status` verifies, rejects, or retires the candidate. `PUT /api/video-quality/runs/{runId}/videos/{videoId}/scenes/{sceneOrder}/lessons/{lessonId}/revision` retires the prior lesson and creates a new candidate revision linked to the same review. Retired lessons stop matching immediately. Prompt snapshots retain applied lesson IDs/revisions along with template prompt version, rule version, model, source hash/revision, and scene settings.

The application only records evidence and suggestions. Sellers decide whether to replace a source image, request a template/rule code change, or verify/revoke a lesson. A normal quality check uses one seller-triggered H3 clip after a change; there is no automatic paid A/B/C generation, fixed 32-clip target, or requirement for three reviewers.

Manual asset selection is frozen when starting a run. For uploads during a waiting run, use automatic selection or cancel/start a newly saved run to change its frozen source IDs. Retry is for failed checkpoints; explicit re-render is offered while waiting for video review. Editing a completed run starts a new run rather than rewriting its approved package.

## Storage and security

Cloudinary media use `authenticated` delivery, unique non-overwriting keys and 10-minute signed access issued only after ownership checks. Both generated AI scene clips and the assembled MP4/thumbnail live in private Cloudinary storage; scene clip keys/versions are in the durable render-job payload, and final video/thumbnail keys are on `promo_videos`. `PromoVideo.ConfigSnapshot` stores the full storyboard and compiled prompt snapshot; each `promo_video_scenes.scene_config` stores that scene's template, settings, prompt version and source-crop metadata. Lease-scoped worker upload grants are not exposed through public workflow APIs. Source hashes/revisions are checked at claim and completion. Cancel or lease loss fences late completion; source approval revoked during render/export also rejects completion. Workflow config refuses credential/provider-routing fields.

The API trusts the authenticated worker's QA report after verifying Cloudinary output identity/version/size. Restrict worker credentials accordingly; this is not independent server-side re-decoding. Cloudinary free-plan quotas and permission to serve authenticated raw ZIP assets must be verified on the actual account. Failed/stale attempts can leave private orphan media; scheduled garbage collection is not included in this MVP.

## Extension and licensing

APCS owns `IVideoRenderer` and the workflow contracts. To add Kling or Seedance, implement `IAiVideoGenerationStrategy`, register it, add its provider/model catalog and credential policy, and preserve the immutable routing keys on planned scenes. Standard/AI mixing remains a follow-up after the AI-only scene flow is validated. Do not enable a mode by changing only the capability flag.

Standard incurs no AI model charges, but render compute, storage and bandwidth still have costs. Remotion's [official license](https://www.remotion.dev/license) currently allows free use for eligible individuals, organizations with up to three employees, non-profits, or non-commercial evaluation. Confirm the legal entity's eligibility before production and recheck when upgrading Remotion; this implementation does not establish license eligibility automatically. [Cloudinary upload/delivery reference](https://cloudinary.com/documentation/image_upload_api_reference) governs authenticated asset behavior.
